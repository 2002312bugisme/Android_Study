# 提示词 ④　章节审查（独立复核）

> **用途**：每章写完后执行一次。**建议与写作分成两次独立任务**，不要在同一次对话里"写完顺便检查"。
> **频率**：高（每章一次）。
> **核心纪律**：**审查阶段不改任何文件**，只出报告；等我明确说"按报告修复"再动手。

---

## 警告：为什么不能让 Agent 自己宣布"已完成"

写完文章 ≠ 文章正确。Android 入门文章最容易出现这些问题：

| 高频错误 | 表现 |
|---|---|
| 把 Android 系统行为说成 Java 语言行为 | "Java 会在 Activity 创建时自动调用 onCreate，因为它继承了 AppCompatActivity" |
| 用旧版 API 解释新版行为 | 讲 `startActivityForResult` 而不提它已废弃（本项目实际用的是新 API） |
| 把没写过的功能说成已实现 | 凭"常见项目都这样"补充 Fragment、RecyclerView |
| 生命周期职责混淆 | 把 `onStart` / `onResume` 的职责混为一谈 |
| 上下文缺失导致误读 | 引用了 `v.getId()` 分发，却没说明是哪个监听器 |
| 同一知识点在三章重复 | 每章都从头讲一遍 `setContentView` |
| 示例改过却没验证能否编译 | 为了讲解方便改写了代码，改完就不成立了 |

所以，**审查必须重新读源码**，不能基于正文自述来"确认没问题"。

## 提示词正文（复制以下内容给 Agent）

```text
你是一名严格的技术审查者。

请审查 docs/android-blog/chapters/<章节文件名>.md 的准确性与教学质量。

项目根目录：D:/Code/Android
审查时请同时读取：
  - 该章节引用的**实际源码、XML 与资源文件**（必须实际打开核对）
  - docs/android-blog/PROJECT_MAP.md 与 SOURCE_INDEX.md
  - 该章的前置章节（检查重复与衔接）
  - 必要的 Android 官方文档（核对与 targetSdk 37 相适配的行为）

═══════════════════════════════════════════
一、检查项
═══════════════════════════════════════════

【1】源码真实性
  - 文中提到的文件路径是否真实存在？
  - 类名、方法名、变量名、资源 ID 是否与源码一致？
  - 引用的代码片段是否遗漏了影响理解的上下文？
  - 是否把"推测"写成了"项目实际行为"？
  - 是否有编造的类、方法、日志、运行结果？

【2】技术准确性
  - Java 语法与 Android API 用法是否正确？
  - 生命周期、Intent、Bundle、View、Drawable、事件分发等概念是否准确？
  - 是否混淆了"我的应用代码 / Android SDK 框架 / AndroidX / 第三方库"这四层的职责？
  - 是否存在版本差异或已废弃的用法被当成现行写法？
  - 关键技术结论是否有足够依据（源码 / 官方文档）？

【3】本项目专属事实（重点核对）
  - 是否误称项目使用了 viewBinding / Fragment / Navigation / RecyclerView /
    ViewModel / 网络 / 存储 / 权限 / 动画 / 自定义 View？
  - 涉及 Material3 主题行为时，是否与主题实际配置
    （Theme.Material3.DayNight.NoActionBar）一致？
  - 涉及生命周期时，是否正确说明"项目仅覆写 onCreate，
    其余行为需实验验证"，而不是当成既有实现？
  - 涉及未注册/被注释的 Activity 时，是否说明了实验前需要先取消注释？
  - 是否把 `Utils` / `DateUtils` 的重复定义误写成"设计模式"？

【4】教学质量
  - 初学者能否理解术语？首次出现的概念是否有解释？
  - 是否解释了代码的**执行顺序**与**设计原因**，而不只是字面翻译？
  - 是否给出可执行或可观察的验证方法？
  - 实验的预期现象是否与代码实际行为一致？
  - 是否存在跳步、重复、空泛总结或为凑字数的内容？

【5】章节质量与格式
  - 是否符合 LEARNING_ROADMAP.md 的整体路线与本章规划？
  - 是否与其他章节重复？（列出重复段落的具体位置）
  - 是否遗漏了本章的核心问题？
  - 是否达到约定篇幅？（用 docs/android-blog/tools/count_chars.py 复核，
    不要凭感觉判断）
  - 章节内链接、代码块语言标注、Markdown 格式是否正确？

═══════════════════════════════════════════
二、输出要求
═══════════════════════════════════════════

先给出审查报告，分成四部分：

  A. 必须修复的问题
     （源码不符、技术错误、编造内容、实验预期错误）
  B. 建议改进的问题
     （表达、结构、可读性、重复）
  C. 已核实且正确的内容
     （列出你实际打开源码确认过的关键结论）
  D. 需要实际运行才能确认的问题
     （静态分析无法判定、必须真机或模拟器验证的）

每个问题都要给出：
  具体位置（章节小节 / 引用的文件与代码位置）
  + 问题原因
  + 建议修改方式

═══════════════════════════════════════════
三、硬性约束
═══════════════════════════════════════════

- **不要修改任何文件**，包括那一章 Markdown 本身。
- 不要因为"读起来顺"就放过事实问题。
- 不要为了显得有产出而编造问题；确实没问题的部分，就明确写"已核实"。
- 只有在我明确要求"按报告修复第 X 章"之后，才修改指定的 Markdown 文件，
  且必须保留原本正确的内容与文章结构。
```

## 审查之后怎么用这份报告

1. **A 类问题（必须修复）**：逐条确认后，再让 Agent 修改。修改时要求：
   - 只改这一章，不动源码；
   - 保留原有正确内容；
   - 改完给出"改了哪几处、分别对应报告第几条"。
2. **B 类问题（建议改进）**：自己判断，不必全改。新手向的文章有时"啰嗦一点"是对的。
3. **D 类问题（需运行确认）**：攒成一份"实验清单"，
   等模拟器（AVD 内存上限 2048 MB）跑起来时一次性验证。
   验证结果可以回填进文章，把"未验证"升级为"已验证"。
4. 每章审查通过后，更新 `README.md` 的章节状态表（⬜ → 🟦 → ✅），
   并做一次单独的 commit。
