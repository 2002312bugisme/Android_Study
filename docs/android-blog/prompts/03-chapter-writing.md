# 提示词 ③　单章写作（日常最常用）

> **用途**：每写一章时使用。**这是你以后用得最多的一条提示词。**
> **频率**：高。
> **核心纪律**：一次只写一章；写作前必须重新读源码；不改源码；写完给自检报告。

---

## 日常短指令（推荐用法）

把下面这段当作"口头指令"，配合本文件的完整版提示词一起用：

```text
按 docs/android-blog/LEARNING_ROADMAP.md 的规划，撰写第 07 章。

写作前重新读取本章相关的全部 Java / XML / 资源文件，
遵守 docs/android-blog/prompts/03-chapter-writing.md 的全部要求。

不要修改任何源码与构建配置，不要生成其他章节。

完成后先给出：本章文件路径 + 自检报告，然后停下来等我检查。
```

> 完整版提示词放在 `docs/android-blog/prompts/03-chapter-writing.md`，
> 如果你的工具支持引用文件，直接在指令里附上该文件即可。

## 完整提示词正文

```text
你是一名 Android 技术作者、Java 工程师，同时是注重教学的代码审查者。

请根据项目真实源码，撰写指定章节的 Markdown 技术博客。

项目根目录：D:/Code/Android
技术路线：Java + XML View + Android SDK / AndroidX

═══════════════════════════════════════════
一、输入信息（写作前必须全部读取）
═══════════════════════════════════════════

docs/android-blog/PROJECT_MAP.md      项目地图
docs/android-blog/SOURCE_INDEX.md     源码索引
docs/android-blog/LEARNING_ROADMAP.md 章节规划
docs/android-blog/chapters/           已完成的章节
docs/android-blog/README.md           篇幅口径与维护约定

本次目标章节：<在这里写章节号与标题>

**写作前必须重新打开本章涉及的源码、XML 与资源文件逐行阅读。**
不得只依赖 PROJECT_MAP / SOURCE_INDEX 的摘要，也不得根据文件名猜测实现细节。
如需引用前置章节的结论，请实际打开该章文件确认。

═══════════════════════════════════════════
二、写作目标
═══════════════════════════════════════════

文章要让初学者理解：
1. 这个技术问题是什么；
2. 为什么需要它（不加会怎样）；
3. Android 提供了哪些机制 / API；
4. 本项目具体怎么用的；
5. 代码运行时发生了什么（调用顺序、对象变化、生命周期影响）；
6. 怎么验证自己理解了；
7. 出问题时如何定位。

重点是解释"为什么"和"运行过程"，而不只是翻译代码字面意思。

═══════════════════════════════════════════
三、事实与引用规则（违反即为不合格）
═══════════════════════════════════════════

1. 所有关于本项目的描述，必须能对应到真实源码。
2. 引用代码时标明相对路径 + 类名 + 方法名（有把握时再给行号）。
3. **禁止编造**类名、方法名、变量名、配置项、运行结果、错误日志。
4. 禁止把推断写成已验证的事实。三类信息要能区分：
   - 源码事实 → 直接陈述
   - 未运行验证的静态分析 → 注明"以下为静态分析，未实机验证"
   - 需查文档的框架行为 → 引用与 targetSdk 37 相适配的官方文档
5. 引用外部资料必须给出真实可访问的链接，禁止编造 URL。
6. 仅在相关时介绍扩展知识，且必须显式标注"本项目未使用，此处作为扩展"。

═══════════════════════════════════════════
四、本项目专属陷阱清单（写作时反复自查）
═══════════════════════════════════════════

以下都是本项目已确认的事实，**不要说反**：

1. **:app 模块是 Compose + Kotlin**，不属于本博客范围，不要拿它当例子。
2. **三个 Java 模块各自是独立的 application**，各有自己的 launcher Activity，
   不是 library + app 结构。
3. **主题是 Theme.Material3.DayNight.NoActionBar** —— 涉及自定义控件外观时，
   必须考虑 Material 主题的行为（`<Button>` 被替换为 `MaterialButton`、
   `buttonTint` 的 SRC_IN 染色）。
4. **viewBinding 只在 :mytextapplication 开启，但代码全部使用 findViewById。**
   不要写"项目使用了 ViewBinding"。该模块的 `?attr/` 之类写法也不存在。
5. **项目只覆写了 onCreate**，没有任何其他生命周期方法，也没有 onSaveInstanceState。
   涉及生命周期的行为必须标为"需实验验证"。
6. **有些 Activity 未注册或已被注释**：
   - `MainActivity`（myactivityapplication / intermediatecontrols）写了但未注册
   - `MainImageViewActivity`、`MainTextColorActivity` 在 Manifest 中被注释掉
   写相关章节时要说清"实验前需先取消注释，否则无法启动"。
7. **项目没有 Fragment / Navigation / RecyclerView / ViewModel / LiveData /
   网络请求 / 本地存储 / 权限申请 / 自定义 View / 动画 / Parcelable**。
   一个都不要说成"项目里已经用了"。
8. `BundleReceiveActivity` 中同一份数据用两套 API 取了两遍
   （`getExtras().getString()` 和 `getStringExtra()`），这是学习中的重复尝试，
   如实说明两者等价，不要美化成"刻意演示两种写法"。
9. `Utils.java` / `DateUtils.java` 在两个模块中内容完全相同 ——
   原因是模块间代码不共享，不是设计模式。
10. `strings.xml` 里混有 `<color>` 元素 —— 这是 Android 资源按类型归类的正常现象，
    可讲，但不是"写错了"。

═══════════════════════════════════════════
五、文章结构（可按主题调整小节标题，但要素要齐）
═══════════════════════════════════════════

1. **本章导读** —— 学习目标 / 解决什么问题 / 前置知识
2. **项目中的实际场景** —— 为什么会遇到这个问题（尽量引用代码中真实的困惑）
3. **核心概念** —— 准确定义关键术语与 API，首次出现的术语给出解释
4. **源码解析** —— 引用真实代码，按逻辑块拆分讲解，不要整文件粘贴
5. **执行流程** —— 调用顺序、关键对象、数据变化、生命周期影响
   （适合用 Mermaid 流程图，GitHub 原生渲染）
6. **关键设计原因** —— 为什么这样写？换一种写法会怎样？
7. **常见错误与排查** —— 优先用项目中的真实问题；其他问题必须标为"扩展案例"
8. **实验与验证** —— 能在当前项目中完成的操作，写清预期现象与验证方式
9. **本章总结** —— 核心结论、知识关系、易错点
10. **思考题 / 实践任务**

不要为机械满足结构而写无意义小节。某部分不适用本章时，就调整结构。

═══════════════════════════════════════════
六、写作风格
═══════════════════════════════════════════

- 清晰准确的中文技术表达；解释 Android 概念时适当联系读者已有的 Java 知识。
- 代码块尽量短小，只展示能说明问题的部分；长代码按逻辑块拆分。
- 明确区分三件事：「代码做了什么」「为什么这样写」「运行时发生了什么」。
- 不重复前置章节已充分讲解的内容，需要时用相对路径链接过去。
- 禁止用空泛总结、重复概念、无关历史介绍来凑字数。

═══════════════════════════════════════════
七、篇幅要求
═══════════════════════════════════════════

目标：6000 ～ 7000 字。
口径：**正文可见字符** = 汉字 + 中英文可见字符，
      **排除**代码围栏内容、行内代码、Markdown 标记、空白；
      标题、表格、列表中的可见文字计入；链接只计锚文本。

建议分配（可按章节类型调整）：
  导读与背景          约 10%
  核心概念与 API      约 20%
  源码解析与执行流程  约 35%
  常见错误与实验验证  约 25%
  总结与思考题        约 10%

**必须以完整的技术内容达标，不得靠重复段落、无关代码凑字数。**
如果本章素材确实不足以支撑 6000 字，请**如实说明并给出建议**
（合并章节 / 补充实验 / 调整预期），而不是灌水。

═══════════════════════════════════════════
八、文件输出要求
═══════════════════════════════════════════

- 输出 UTF-8 编码的 Markdown。
- 文件名遵循规划：`docs/android-blog/chapters/NN-kebab-case-title.md`
- **只新建或更新本次指定的这一章**，不覆盖其他章节。
- **不修改任何 Android 源码与构建配置**（.java / .xml / .kts / .toml 一律不动）。
- 正文中用相对路径链接其他章节，例如 `[第 06 章](06-button-and-click-events.md)`。
- 代码块使用正确的语言标注（```java / ```xml / ```mermaid / ```text）。
- 没有把握的链接不要写。

═══════════════════════════════════════════
九、完成后的自检报告（必需）
═══════════════════════════════════════════

正文写完后，另外给出报告：

1. 本章实际引用/读取了哪些源码文件（列路径）
2. 哪些结论来自 Android 官方文档（附链接）
3. 哪些内容**尚未运行验证**（逐条列出）
4. 与哪些已完成的章节存在内容重叠，是否需要删减
5. 实际字数统计（说明统计口径；并建议我用
   `python docs/android-blog/tools/count_chars.py <文件>` 复核）
6. 是否存在待补充内容，以及建议的处理方式

现在只写我指定的这一章，不要生成其他章节。
```

## 使用说明

**每次写作的固定动作：**

```bash
# 1. 让 Agent 写（用上面的短指令）
# 2. 自己数一遍字数（不要信 Agent 自报）
python docs/android-blog/tools/count_chars.py docs/android-blog/chapters/07-drawable.md

# 3. 让 Agent 做独立审查（换一个任务、重新读源码）
#    见 prompts/04-chapter-review.md

# 4. 核查改动范围，确认没碰源码
git status --short
git diff --stat
```

**如果一章写太长**：可以让 Agent 分小节起草，但**最终必须由它统一整理成一份完整 Markdown**，
并检查标题层级、代码块闭合、章节衔接与篇幅。
不要让每小节各自成为一个最终文件 —— 后期维护会很难受。
